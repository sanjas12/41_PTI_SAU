# PTI SAU

Desktop-приложение для генерации, визуализации и передачи технологических сигналов по **Modbus TCP**. Проект предназначен для наладки, тестирования и отладки систем автоматизации без необходимости подключать реальные источники сигналов.

Приложение разрабатывается как Windows desktop application на **Python 3.8.10 + PyQt5**.

---

## 1. Назначение проекта

**PTI SAU** позволяет имитировать технологические аналоговые сигналы, управлять ими вручную или с помощью сценариев, отображать изменения на графиках и передавать значения внешнему промышленному оборудованию через Modbus TCP.

Основной сценарий использования:

```text
PTI SAU
   │
   ├── Генерация сигналов
   │      ├── Sine
   │      ├── Square
   │      ├── Sawtooth
   │      ├── Random
   │      └── Custom
   │
   ├── Визуализация
   │      └── PyQtGraph
   │
   ├── Ручное управление
   │
   ├── Сценарии
   │      └── Scenario Engine
   │
   └── Modbus TCP
          │
          ▼
       PLC / АСУ ТП
```

Программа может использоваться для:

* тестирования PLC;
* проверки Modbus TCP-взаимодействия;
* наладки систем автоматизации;
* имитации датчиков;
* проверки алгоритмов управления;
* воспроизведения заранее заданных сценариев;
* визуального контроля генерируемых сигналов.

## 2. Основные возможности

### Каналы

Поддерживается работа с несколькими аналоговыми каналами.

Для канала могут задаваться:

* имя;
* тип сигнала;
* минимальное значение;
* максимальное значение;
* частота;
* текущее значение;
* состояние канала.

Предусмотрена работа с 20 и более каналами.

### Типы сигналов

Планируется/поддерживается генерация:

* синусоидального сигнала (`Sine`);
* прямоугольного сигнала (`Square`);
* пилообразного сигнала (`Sawtooth`);
* случайного сигнала (`Random`);
* пользовательского сигнала (`Custom`).

### Визуализация

Для отображения сигналов используется **PyQtGraph**, что позволяет эффективно обновлять графики в режиме, близком к реальному времени.

### Режимы управления

Предусмотрены два основных режима:

```text
┌────────────────────────────────────────────┐
│ Управление каналами                        │
│                                            │
│  [ Ручной ]              [ Сценарий ]      │
│                                            │
│  ┌──────────────────────────────────────┐  │
│  │                                      │  │
│  │        QStackedWidget                │  │
│  │                                      │  │
│  │  Ручной режим: сетка каналов         │  │
│  │  Сценарий: конструктор сценариев     │  │
│  │                                      │  │
│  └──────────────────────────────────────┘  │
└────────────────────────────────────────────┘
```

Общие элементы управления не зависят от выбранного режима.

## 3. Архитектура

Проект разделён на несколько основных слоёв:

```text
┌───────────────────────────────────────────────┐
│                    UI Layer                   │
│                    PyQt5                      │
│                                               │
│ MainWindow / Widgets / Settings / Plots       │
└───────────────────────┬───────────────────────┘
                        │
                        ▼
┌───────────────────────────────────────────────┐
│                   Core Layer                  │
│                                               │
│ Channel / SignalGenerator / Engine            │
└───────────────┬───────────────────┬───────────┘
                │                   │
                ▼                   ▼
┌──────────────────────┐   ┌──────────────────────┐
│      PyQtGraph       │   │     Modbus Layer     │
│      Visualization   │   │     Modbus TCP       │
└──────────────────────┘   └──────────┬───────────┘
                                      │
                                      ▼
                              ┌───────────────┐
                              │      PLC      │
                              │  Schneider    │
                              │ M340 / M580   │
                              └───────────────┘
```

### Основные принципы

* UI не должен содержать бизнес-логику генерации сигналов.
* Сетевые операции Modbus не должны блокировать GUI-поток.
* Генерация сигналов должна быть отделена от визуализации.
* Адресация Modbus должна быть отделена от реализации клиента.
* Настройки приложения должны быть отделены от настроек пользовательского интерфейса.
* Сценарии должны быть независимы от конкретных Qt-виджетов настолько, насколько это возможно.

### `src/ui`

* главное окно;

* графики;
* настройки;

### `src/core`

Основная бизнес-логика приложения:

* модель канала;
* генерация сигналов;
* типы сигналов;
* основной движок.

Это наиболее важный слой для unit-тестирования.

### `src/modbus`

Работа с Modbus TCP:

* клиент;
* карта регистров;
* асинхронное выполнение сетевых операций.

Сетевые операции не должны выполняться непосредственно в GUI-потоке.

### `src/scenario`

Работа со сценариями:

* модель сценария;
* движок выполнения;
* пользовательский интерфейс конструктора.

### `src/config`

Работа с конфигурацией приложения:

* загрузка;
* сохранение;
* значения по умолчанию.

### `src/utils`

Общие технические компоненты:

* логирование;
* собственные исключения.

В `utils` не следует размещать бизнес-логику.

## 9. Тестирование

Запуск всех тестов:

```bash
uv run pytest
```

Запуск с отображением coverage:

```bash
uv run pytest --cov=src
```

Запуск конкретного теста:

```bash
uv run pytest tests/test_signal_generator.py
```

### Приоритетные области тестирования

В первую очередь должны тестироваться:

1. генератор сигналов;
2. модель канала;
3. Modbus mapping;
4. сценарный движок;
5. конфигурация.

Особенно важно тестировать граничные случаи:

* `min == max`;
* нулевая частота;
* отрицательная частота;
* большие значения частоты;
* выход за диапазон;
* включение/выключение канала;
* переходы состояний сценария;
* преобразование `Float32` в Modbus registers;
* порядок байтов;
* знаковость `INT16`;
* Modbus offsets.

## 13. Modbus TCP

Приложение предназначено для взаимодействия с промышленным оборудованием через Modbus TCP.

Архитектурно Modbus разделён на:

```text
modbus_client.py
        │
        ├── соединение
        ├── чтение
        └── запись
                │
                ▼
modbus_mapping.py
        │
        ├── каналы
        ├── регистры
        ├── типы данных
        └── преобразования
```

Асинхронные операции должны выполняться через `worker.py` или другой механизм фонового выполнения, чтобы сетевые операции не блокировали Qt GUI thread.

### Пример карты регистров

Концепция адресации:

```text
Channel 1 → 40001-40002
Channel 2 → 40003-40004
Channel 3 → 40005-40006
...
```

Точная карта регистров должна определяться в `modbus_mapping.py`.

При работе с `Float32` необходимо отдельно контролировать:

* порядок регистров;
* порядок байтов;
* endianness;
* Modbus offset;
* signed/unsigned representation.

## 14. Сценарии

Сценарный режим предназначен для автоматического воспроизведения последовательности состояний и значений каналов.

Архитектура:

```text
Scenario Model
      │
      ▼
Scenario Engine
      │
      ├── Channel values
      ├── Timing
      ├── State transitions
      └── Execution
      │
      ▼
     Core
```

Пользовательский интерфейс конструктора сценариев не должен напрямую реализовывать алгоритм выполнения сценария.

### Основные состояния

В сценарном движке необходимо поддерживать корректные переходы между состояниями, например:

```text
STOP
  │
  ▼
START
  │
  ▼
RUNNING
  │
  ├── PAUSE
  │     │
  │     ▼
  │   RESUME
  │
  ▼
STOP
```

## 18. Безопасность

Приложение работает с промышленным сетевым оборудованием, поэтому необходимо соблюдать следующие правила:

* не хранить пароли и секреты в Git;
* не записывать секреты в лог;
* не использовать реальные IP-адреса оборудования как значения по умолчанию без необходимости;
* валидировать IP-адреса и порты;
* корректно обрабатывать потерю Modbus-соединения;
* устанавливать разумные сетевые timeout;
* не блокировать GUI-поток сетевыми операциями;
* явно обрабатывать некорректные значения сигналов.

Особое внимание необходимо уделить ситуации, когда PLC отключается во время работы приложения.

## 22. Контроль качества перед релизом

Перед созданием релизной версии рекомендуется выполнить:

```bash
uv run ruff check .
```

```bash
uv run ruff format --check .
```

```bash
uv run pytest
```

```bash
uv run pytest --cov=src
```

После успешного прохождения проверок выполнить сборку Windows-приложения.

Минимальный критерий релиза:

```text
Ruff        ✓
Formatting  ✓
Tests       ✓
Coverage    ✓
Build       ✓
Manual test ✓
Modbus test ✓
```

## 24. Примечания разработчика

### Python

Проект намеренно ограничен Python 3.8.10 из-за требований целевой среды.

Изменение версии Python следует выполнять только после проверки совместимости:

* PyQt5;
* PyQtGraph;
* NumPy;
* Modbus-библиотеки;
* cx_Freeze;
* целевой Windows-платформы.

### Windows 7

Поддержка Windows 7 является дополнительным ограничением проекта. При обновлении зависимостей необходимо отдельно проверять, не прекращена ли поддержка Windows 7 соответствующей библиотекой или инструментом сборки.

## 27. Краткая схема проекта

```text
                         PTI SAU
                            │
             ┌──────────────┴──────────────┐
             │                             │
          Manual                       Scenario
             │                             │
             └──────────────┬──────────────┘
                            │
                            ▼
                       Core Engine
                            │
                 ┌──────────┴──────────┐
                 │                     │
                 ▼                     ▼
          Signal Generator          Channel
                 │                     │
                 └──────────┬──────────┘
                            │
              ┌─────────────┴─────────────┐
              │                           │
              ▼                           ▼
         PyQtGraph                    Modbus TCP
              │                           │
              ▼                           ▼
          Operator                       PLC
```

**PTI SAU** — инструмент для имитации технологических сигналов, визуального контроля и тестирования промышленной системы автоматизации через Modbus TCP.
