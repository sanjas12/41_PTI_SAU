# AGENTS.md

## Назначение проекта

`PTI_SAU` — настольное инженерное приложение для генерации аналоговых
сигналов и обмена с PLC Modicon Premium по Modbus TCP. Интерфейс построен на
PyQt5, графики — на pyqtgraph. Приложение рассчитано прежде всего на Windows и
собирается в standalone-приложение через cx_Freeze.

## Среда и зависимости

- Поддерживаемая версия Python: только 3.8 (`>=3.8,<3.9`). Не использовать
  синтаксис и API более новых версий Python.
- Основной менеджер окружения и зависимостей: `uv`.
- Runtime-зависимости: NumPy, PyQt5, pyqtgraph и pyModbusTCP.
- `requirements.txt` генерируется из `pyproject.toml`; не редактировать его
  вручную без необходимости синхронизировать оба файла.
- Основная целевая ОС — Windows. Нужно сохранять совместимость со сборкой
  cx_Freeze и заявленной поддержкой Windows 7.
- `scripts/recreate_env.sh` удаляет и полностью пересоздаёт `.venv`.
- `scripts/build.sh` собирает standalone-приложение через cx_Freeze.
- `scripts/build_all.sh` последовательно запускает пересоздание окружения и
  сборку; для обычной повторной сборки предпочтительнее `build.sh`.

Базовые команды:

```bash
uv sync --group dev --group build
uv run python src/main.py
uv run pytest -q
uv run ruff check src tests build.py
uv run ruff format --check src tests build.py
pre-commit run --all-files
```

Если локальная `.venv` ссылается на удалённый интерпретатор Python, её нужно
пересоздать через `uv`; не считать ошибки запуска такой `.venv` ошибками кода.

## Структура и ключевые компоненты

- `src/main.py` — точка входа и настройка логирования.
- `src/core/` — модели каналов, типы и генерация сигналов; эта логика по
  возможности должна оставаться независимой от Qt.
- `src/scenario/` — модель, движок и UI сценариев.
- `src/modbus/` — низкоуровневый Modbus-клиент и фоновые задачи.
- `src/plc/` — преобразование значений каналов в регистры PLC и их обмен.
- `src/ui/` — окна и виджеты PyQt5.
- `src/ui/main_window.py` сейчас является главным координатором приложения.
- `build.py` и `scripts/build.sh` отвечают за сборку cx_Freeze.
- `tests/` — автоматические тесты. Новую чистую бизнес-логику сопровождать
  unit-тестами.

Импорты сейчас рассчитаны на запуск `src/main.py`, например `from core...` и
`from ui...`. Не менять схему пакетов и импортов частично: такая реорганизация
должна выполняться отдельно и с проверкой запуска и сборки.

## Правила предметной логики

- В `AnalogChannel` амплитуда и смещение задаются в процентах.
- В генераторе `amplitude` и `offset` трактуются как проценты от половины
  диапазона канала:

  ```text
  value = midpoint + (raw * amplitude + offset) * half_range
  ```

- Итоговое значение ограничивается `min_value` и `max_value`.
- RANDOM хранит отдельное нормализованное значение в диапазоне `[-1, 1]` и
  удерживает его 100 мс. Нельзя использовать `current_value` как RANDOM raw:
  `current_value` уже масштабирован.
- `ScenarioEngine` изменяет параметры каналов, а фактические значения считает
  общий `SignalGenerator`.
- Параметры сценария `ramp_up` и `ramp_down` присутствуют в модели и UI, но
  плавные переходы пока фактически не реализованы.

## PLC и безопасность изменений

- Связь с реальным оборудованием считается чувствительной частью проекта.
- Не менять карту регистров, адреса, Unit ID, порядок байт/слов REAL, частоту
  записи или способ пакетной записи без явного согласования и проверки на PLC.
- Текущая карта начинается с аналоговых сигналов по адресу 0, управления по
  адресу 40 и статуса по адресу 50.
- Для одного REAL используются два 16-битных регистра с текущим порядком
  `struct.pack("<f")` / `struct.unpack("<HH")`.
- Не запускать тесты, которые подключаются к реальному PLC, без явной просьбы
  пользователя. Для автоматических тестов использовать mock/fake Modbus-клиент.
- Не выводить пароли, приватные адреса, токены или содержимое чувствительных
  конфигураций в логи и ответы.

## Стиль и качество

- Соблюдать Ruff из `pyproject.toml`: Python 3.8, длина строки 88, двойные
  кавычки.
- Новые и изменяемые функции аннотировать. При допустимом `None` использовать
  явный `Optional[T]`, поскольку mypy запрещает implicit Optional.
- Для числового состояния явно сохранять нужный тип (`0.0` для `float`), чтобы
  mypy не выводил атрибут как `int`.
- Не подавлять ошибки через новый `except Exception: pass`. Ожидаемые ошибки
  перехватывать конкретно и логировать с полезным контекстом.
- Не добавлять новый `print()` в рабочую логику; использовать `logging` или
  Qt-сигналы журнала согласно слою приложения.
- Не смешивать новый файловый ввод-вывод с UI, если его можно вынести в
  отдельный сервис или repository.
- Сохранять изменения небольшими. Крупное разделение `main_window.py`,
  `plot_widget.py` и других больших UI-модулей выполнять отдельными этапами.

## Проверка изменений

- Для исправления сначала добавить регрессионный тест, если логика допускает
  автоматическую проверку.
- Запускать как минимум тесты затронутого модуля, Ruff check, Ruff format check
  и mypy/pre-commit.
- Для изменений UI выполнить хотя бы проверку импорта/создания виджета без
  подключения к PLC; ручную GUI-проверку явно указать в результате.
- Для изменений сборки проверить cx_Freeze отдельно; обычные unit-тесты не
  подтверждают работоспособность EXE.
- Не утверждать, что проверка пройдена, если команда не запускалась или была
  заблокирована окружением.

## Git и взаимодействие с пользователем

- Коммиты выполняет пользователь. Не выполнять `git commit`, `git push`,
  создание тегов или публикацию релиза без его прямой просьбы.
- Не добавлять файлы в staging (`git add`) без прямой просьбы. После изменений
  сообщать пользователю, какие файлы нужно добавить повторно, особенно если
  pre-commit или форматтер изменил уже staged-файл.
- Не удалять и не перезаписывать несвязанные пользовательские изменения.
- Перед редактированием проверять `git status --short` и отличать существующие
  изменения пользователя от изменений текущей задачи.
- Формат сообщений коммитов проверяется conventional-pre-commit. Допустимые
  типы включают `feat`, `fix`, `docs`, `style`, `refactor`, `test`, `chore`,
  `ci`, `perf`, `bump` и `build`.
- В конце каждого итогового ответа предлагать одну готовую строку сообщения
  коммита для выполненных изменений. Коммит не выполнять.
- Следовать стилю истории проекта: Conventional Commits, при необходимости
  область в скобках и краткое русскоязычное описание со строчной буквы,
  например `feat(ui): улучшить отображение настроек канала`.

## Известные ограничения проекта

- Автоматическое покрытие тестами пока небольшое.
- Runtime-настройки загружаются после вычисления части модульных констант, из-за
  чего пользовательские настройки могут применяться не полностью.
- Главное окно и некоторые UI-модули слишком велики и объединяют несколько
  ответственностей.
- В текущей архитектуре существуют отдельные Modbus-клиенты в `MainWindow` и
  `PLCInterface`; объединять их нужно отдельным безопасным изменением.
- Периодическая запись PLC пока не обеспечивает полноценный backpressure и при
  медленной связи может создавать очередь фоновых задач.
- Корневой `settings.json` может быть пустым; загрузчик откатывается к значениям
  по умолчанию, но файл следует привести к валидному JSON.
- В `pyproject.toml` указан `README.md`, тогда как в репозитории используется
  `Readme.md`; это потенциальная проблема на регистрозависимых файловых системах.
